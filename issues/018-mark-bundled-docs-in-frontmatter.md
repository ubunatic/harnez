# 018 — Bundled docs don't self-identify as harnez-managed

**Status:** Closed — resolved in e371540 (backfill), 9a5081d (guard test)

## Context

Found 2026-08-16 doing an `/evergreen` pass across `uman`, `books`, and
`ubunatic.com` after a working session. Deciding which `docs/*.md` were
safe to hand-edit (project-local architecture/decision notes) versus which
would be silently overwritten on the next `apply` (harnez-bundled)
required finding this line in each project's `AGENTS.md`/`CLAUDE.md`:

```
Docs in `./docs/` are managed by harnez. <!-- harnez:bundled -->
```

(`internal/claude/apply.go:336`, `buildLangConventions`). That marker lives
**only** in the generated `AGENTS.md` "Language Conventions" block — the
bundled doc files themselves (`docs/Canary.md`, `docs/Compliance.md`,
`docs/Make.md`, `docs/Markdown.md`, `docs/Git.md`, `docs/Spec.md`, per-language
docs, …) carry a `title:`/`weight:` front-matter block (see
`installDoc`/`langDocState` in `apply.go`) but nothing that says "this file
is centrally managed, edit the harnez source instead."

Opening `ubunatic.com/docs/Canary.md` directly — the normal way an agent or
a human reads a doc — gives no signal that it differs from
`ubunatic.com/docs/Publishing.md` (project-local, safe to edit) sitting
right next to it in the same directory. The only way to know is to already
know to check `AGENTS.md`, which most doc-reading flows won't do.

This is the same discoverability gap issue 017 hit from a different angle
(a bundled doc's *content* was wrong for the receiving project); here the
problem is that a bundled doc's *managed status* isn't visible from the doc
itself at all.

## Proposal

Add a front-matter key to every doc installed via `installDoc` that marks
it as harnez-managed, e.g.:

```yaml
---
title: Canary-First Development
weight: 20
managed-by: harnez
---
```

Concretely:

1. Add `managed-by: harnez` (or reuse `harnez:bundled` as an
   HTML-comment convention, matching what `AGENTS.md` already uses) to the
   source docs under `docs/` and `docs/lang/` in this repo.
2. `installDoc` already copies bytes verbatim, so no code change is needed
   there — the marker travels for free once it's in the source.
3. Optionally, have `langDocState`'s existing "bundled"/"custom"/"not
   installed" classification surface *why* — right now that logic already
   knows the answer (byte comparison against the bundled source) but only
   exposes it via `harnez status`, not by looking at the file.
4. Downstream `docs/README.md` index files could reflect the marker
   automatically instead of every project hand-annotating which rows are
   bundled (`ubunatic.com/docs/README.md` currently doesn't distinguish at
   all).

## Non-goals

Not proposing to duplicate the full `AGENTS.md` bundled-docs list into every
file's front matter, or to block hand-edits — projects will drift locally
over time and that's expected (`langDocState` already has a "custom"
classification for exactly this). This is purely about a doc announcing its
own provenance to anyone who opens it directly, the same way `weight:`
already announces its place in the sidebar. Checked while filing this:
`ubunatic.com/docs/Canary.md` is currently byte-identical to the
harnez source (`diff` returns clean), so today it's purely a
provenance-signaling gap, not yet a drift-tracking one.

## Implementation Plan

**Partially resolved already.** Since filing, the convention landed as an HTML
comment *below* the front matter rather than a `managed-by:` front-matter key:

```markdown
---
title: Make Conventions
weight: 62
---

<!-- harnez:bundled -->
# Make Conventions
```

`internal/claude/docs_capture.go:330` already reads this marker
(`strings.Contains(data, "<!-- harnez:bundled -->")`) to decide whether a
project-local doc is harnez-managed, so the marker is now load-bearing code,
not just a comment. Remaining work is **coverage + enforcement**, not design.

### Current coverage (audited while planning)

| Dir | Marked | Unmarked |
|---|---|---|
| `docs/lang/` | Bash, Cpp, Git, Go, Make, Markdown, Rust, Zig | **GTK4.md** |
| `docs/practices/` | IssueTracking | **AgenticLoop, ConciseMode, DeploymentTransparency, GoRelease** |
| `docs/other/` | — | **Canary, Containerfile, SharedDiskCache, Spec, Website** |

10 of 20 copyable docs are unmarked.

### Steps

1. **Backfill the marker** into the 10 unmarked files: insert
   `<!-- harnez:bundled -->` on its own line immediately after the closing
   `---` of the front matter and before the `# Title` heading, exactly matching
   the marked files' layout (blank line before and after). No other content
   change. Do not touch `docs/` root copies or `docs/studies/` /
   `docs/proposed/` — the root copies are generated by `init` and will pick the
   marker up on the next sync.
2. **Add a guard test** so a new copyable doc can't be added unmarked. Natural
   home is `internal/claude` (where `docs_capture.go` reads the marker) or the
   existing `make lint` target, which already checks `commands/*.md` are
   registered in `config.yaml`. Preferred: a Go test that walks every
   `source:` path declared under `agents_md.languages` and `docs` in
   `config.yaml` (via the embedded FS, so it covers exactly the set that
   actually gets installed) and fails if the file lacks the marker. Testing off
   `config.yaml`'s declared sources rather than a `docs/*/` glob avoids
   false-failing on files that exist but aren't installed.
3. **Re-sync generated copies**: `make apply` + `make init` so
   `~/.claude/docs/*.md` and this repo's `docs/*.md` root copies carry the
   marker. Sibling projects pick it up on their next `harnez init`
   (or an `/harnez-sync` sweep).
4. **Optional, only if cheap**: have `docs/README.md`'s copyable-docs tables
   note the marker convention in one line, so a reader of the index knows what
   `<!-- harnez:bundled -->` means. Skip the ticket's §4 proposal to
   auto-generate downstream `docs/README.md` rows — that's a separate feature
   (index generation), not provenance signalling.

### Design decisions

- **Keep the HTML comment; do not add a `managed-by: harnez` front-matter key.**
  The comment is already parsed by `docs_capture.go` and already used in
  `AGENTS.md`; adding a second, parallel marker in front matter would create
  exactly the drift this ticket complains about. Update the ticket's §Proposal
  wording accordingly when implementing.
- **Marker after the front matter, not inside it**, matching the 10 files that
  already have it — front matter is consumed by the website generator
  (`title:`/`weight:`), and an unknown key there is noise for that consumer.
- **Ticket's §3** (make `langDocState` explain *why* a doc is bundled/custom)
  is out of scope: `langDocState` compares bytes against the embedded source,
  which is strictly stronger evidence than a marker, and it already reports
  `bundled`/`custom`/`not installed`. Note in passing that `langDocState`
  compares against the raw bundled bytes while `installDoc` writes
  `markdown.MergeManagedDoc(...)` output — for a doc with a local stop marker
  these differ, so such a doc always reports `custom`. That's a pre-existing
  wrinkle, worth a separate ticket, not this one.

### Risks / open questions

- Backfilling changes bytes in 10 bundled docs, so every downstream project
  that has an unmodified copy will show a one-line diff on its next `init` —
  expected and harmless, but a sync sweep will report churn across all siblings
  at once. Land it as a single commit so the churn is explainable.
- A project that hand-edited a bundled doc keeps the marker while diverging
  from the source. That's acceptable (`langDocState` already classifies it
  `custom`); the marker signals provenance, not currency.

### Scope

**Small** — 10 mechanical one-line doc insertions, one guard test, one sync run.
