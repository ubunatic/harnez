## Pi Durable and “Level 3: out of the loop”

1. **“Pi Durable” most precisely means Earendil Works’ experimental `@earendil-works/pi-durable` package**, in the Pi (`earendil-works/pi`, formerly `badlogic/pi-mono`) ecosystem created by Mario Zechner. It is a storage-backed agent harness for multi-conversation applications, distinct from Pi’s interactive, single-user coding-agent CLI. It commits conversation entries, model/tool turns, tasks, and app documents before exposing state; reopening storage resumes unfinished work. The project calls the API experimental and changeable. Sources: https://github.com/earendil-works/pi/tree/main/packages/durable and https://github.com/earendil-works/pi/blob/main/packages/durable/README.md
2. **Do not conflate this with `disler/durable-pi`**: that separately named project is an application/network using Pi Durable. Its README describes a per-device `dpi-backend`, SQLite-owned agents, bearer-token clients, and web/TUI/curl clients; agent execution stays on the device. Source: https://github.com/disler/durable-pi
3. **Harness architecture:** `Harness.open(storage, {models, registry, ...})` opens a session; `root()` yields a persisted conversation, `submit()` durably admits inputs and returns a reacquirable `Submission`, and registered tasks/extensions/tools run through the harness. Storage choices documented include memory, JSONL, and SQLite; `@earendil-works/chord` supplies transactional document state and `pi-ai` model access. See `packages/durable/README.md` sections “Persist and Resume”, “Extensions”, and “Watching a Conversation”.
4. **Recovery semantics:** `harness.resume()` starts scheduling persisted unfinished tasks; submit/wait also starts the scheduler. Submissions accept `requestId` for deduplicating retried admission. Tools declare replay safety: a safe interrupted call can be retried; a non-safe effect must be surfaced as interrupted rather than blindly repeated. This is not universal exactly-once execution: external side effects need idempotency/compensation at their boundary. A provider UUIDv7 session identity persists across reopen/retry/reset/compaction/model changes.
5. **Persistence and observation:** transcript entries are immutable; document changes and entries commit atomically. `viewState()` is a live structural view; `watch()` streams committed Chord operations, and `watchEvents()` derives coding-agent-style JSON event batches plus an initial snapshot. Slow consumers are bounded (100 frames/batches) and get the newest view/snapshot; clients reconnect from current state rather than replaying an unbounded event stream. Partial generation/tool output is committed up to every 100 ms (documented possible loss window).
6. **Server/client and protocol distinction:** the core harness is a library/runtime, not a prescribed server protocol. It exposes state/watch APIs usable by a host’s client transport. The `durable-pi` app supplies device HTTP backend/client separation. Pi Coding Agent’s own `--mode rpc` is a separate JSON-lines stdin/stdout protocol with commands, correlated responses, and streamed events—not evidence that Durable itself is an RPC server. Sources: https://github.com/earendil-works/pi/blob/main/packages/durable/README.md ; https://github.com/disler/durable-pi ; https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md
7. **Origin / implementation paths:** Mario Zechner is the Pi ecosystem author; Earendil Works maintains the durable package. Useful source paths in the canonical repo: `packages/durable/README.md`, `packages/durable/src/` (Harness, task/scheduler, session/storage and watch/event implementation), `packages/durable/test/examples/19-json.ts` (JSON event stream), and `packages/durable/test/examples/23-subagent-background.ts` (persistent subagents). I found no evidence that Zechner coined the generic phrase “durable execution”; it is established workflow/runtime terminology.
8. **“Level 3: out of the loop” is ambiguous, not a recognized universal coding-agent level.** A result bearing that exact label exists in a secondary AI-governance taxonomy, but no evidence ties it to Pi or a broadly accepted coding-agent taxonomy: https://github.com/BridgeCoreAI/ai-grc-engineering/blob/main/frameworks/nist-ai-rmf/references/human-oversight-levels.md. Say which scale is intended before treating the number as meaningful.
9. **Canonical nearby taxonomies differ:** Sheridan & Verplank’s 1978 ten-level human/automation ladder ranges from manual to full automation; Parasuraman, Sheridan & Wickens (2000) organize automation across information acquisition, analysis, decision/action selection, and implementation, each with low-to-high levels. “Out-of-the-loop” describes a human-factors condition/problem (operator lacks engagement/situation awareness), not uniquely level 3. Primary sources: https://ntrs.nasa.gov/api/citations/20020039536/downloads/20020039536.pdf ; https://www.cs.uml.edu/~holly/91.550/papers/sheridan-autonomy.pdf
10. **Another plausible meaning:** a modern 0–5 human oversight scheme may label Level 3 “supervised automation” (human monitors/intervenes), with out-of-loop/full automation at Levels 4–5; aviation taxonomies likewise distinguish supervised, manage-by-exception, and full automation. Thus “Level 3 = out of loop” can invert these scales. The label needs its source taxonomy. Aviation taxonomy example: https://cloud-platform-e218f50a4812967ba1215eaecede923f.s3.amazonaws.com/uploads/sites/54/2025/01/Aviation-autonomy-CP-Feb-2024-1.pdf
11. **Comparables (scope only):** Temporal stores durable event histories and replays deterministic workflow code to reconstruct state; Pi instead persists task/conversation/document commits and resumes scheduled work, with explicit tool replay policy. DBOS checkpoints workflow steps in a database, closer at step-recovery level. Cloudflare Durable Objects provide a uniquely addressed compute+transactional-storage actor; their runtime may evict/restart instances, so applications persist state incrementally. None implies autonomous decision authority: durability is recovery behavior, orthogonal to human oversight/autonomy. Sources: https://docs.temporal.io/encyclopedia/event-history ; https://docs.dbos.dev/python/examples/widget-store ; https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/

## Harnez as a durable, client-independent agent server
Read-only audit, 2026-10-20. Recommendation: extract the existing lifecycle into a server-owned execution service; initially promise recovery at provider-turn boundaries, then add finer checkpoints where adapters expose tool execution. No repository changes or live agent runs were made.
**Terms.** Pi Durable is a storage-backed task state machine: generation/tool tasks checkpoint phases, persist waits and reuse recorded nested results; interrupted effects still require replay policy and idempotency. It is more than a saved transcript or detached subprocess ([upstream README](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md)). “Level 3” has conflicting public taxonomies; here use the requested operational meaning: a goal runs unattended within delegated authority, with verified completion or a durable blocked outcome. Keep this definition explicit rather than importing a purported universal level number. Pi’s Cloudflare integration currently lacks tool approvals and cursor-based event replay, so it is a reference, not a complete governance blueprint ([limitations](https://developers.cloudflare.com/agents/harnesses/pi/)).
**Existing foundation.** `internal/subagent/session.go` persists identity, provider session IDs, ancestry, role, workdir, process identities, quota/quarantine state, usage and bounded reply history under `~/.harnez/agents`; name creation uses a registry flock and exclusive creation, updates use temporary-file rename. `driver.go` normalizes Claude, Codex, AGY and Pi run/resume/compact/stop/delete; streaming is capability-dependent. `resume.go` uses native provider history, with a spec-matched stale-session fallback to a fresh session. `cmd/harnez/agent_run.go` already checks concurrent writers, lineage, quota and compaction. This is substantial reusable lifecycle infrastructure, not yet an execution journal.
**Compaction/quota and ownership.** `compact.go`, provider adapters and `spec/agent.yaml` implement context thresholds and provider compaction; acknowledgements and lower context counts matter, while AGY has distinct limitations. Before/after quota readings, exhausted-quota refusal, alternatives, Codex recovery probes/quarantine and token telemetry already exist. These do not constitute a persisted scheduler with reset-time wakeups or cross-provider continuation. Provider-native transcripts cannot be transferred losslessly between providers; retain their references and create explicit handoff branches with summaries, artifacts and provenance. `docs/HarnezAgentArchitecture.md` is partly stale: it still advertises the fixed Claude #498 limitation and MCP async arguments no longer exposed by the current tool schema; trust code over those passages.
**Clients today and gaps.** `internal/mcp/server.go` offers stdio MCP lifecycle tools by invoking CLI commands; spawn/resume are synchronous, and `harnez_command` supplies host-background guidance. `agent_async.go` retains detached-worker machinery, but the normal policy is a host-owned `HTO=0` job. `agent_send.go` routes Claude plugin channels, Codex queue messages and supervised AGY control sockets. `internal/channel` has local registrations and receipt tracking: accepted, queued, received and completed are different states. `internal/tui/jobs/jobs.go` owns shell jobs in the UI goroutine, with process groups, bounded output and completion callbacks; its registry is in memory. Missing are a common independently running supervisor, durable input queue/outbox, canonical ordered events, reconnect cursors, transactional scheduling, recovery leases and authenticated remote session ownership. Atomic JSON rename avoids torn reader views; it does not supply transactional task transitions or power-loss durability.
**Target architecture.** CLI/TUI, Claude/Codex/AGY MCP bridges, web, chat/Slack and cloud clients → authenticated adapters → `harnez serve` → session/task service, scheduler and isolated workers → provider drivers. Start with a per-user Unix socket supervised by the OS; remote TLS access is a later deployment mode. Keep `apply` global and `init` project-local; neither becomes server startup. Put new endpoints, limits and policy defaults in `spec/` plus schemas. Extract orchestration from Cobra handlers so both local compatibility paths and server workers call one service API.
**Store and protocol.** Use transactional SQLite/WAL initially: sessions/conversation branches, submissions with client idempotency keys, tasks/attempts, leases with fencing generations, ordered events, checkpoints, artifact references, approvals, quota wakeups and notification outbox. Commit task state, event and outbox entry together; bound logs and retention. Define one versioned JSON-RPC domain API with capability discovery, submit/status/cancel, approval decisions and subscribe-after-cursor; offer a snapshot when history expires. MCP is an adapter for tool-oriented clients; evaluate ACP as the editor-facing adapter through a canary, without making either protocol the database model. Web can consume a resumable SSE event stream. A notification only advances to delivered/acknowledged according to adapter capability; no assumption that Codex or every host can wake an agent on receipt.
**Recovery and autonomy.** Persist submission acceptance before execution, record attempts and provider IDs as soon as observable, and reconcile expired leases against worker identity on restart. Reattach a surviving worker where supported; otherwise resume the known provider session or mark an uncertain outcome for reconciliation. Never blindly replay a whole interrupted shell/tool turn: effects may have happened before their results were stored. Record replay-safe results; require idempotency keys, postcondition checks or explicit handling for uncertain effects. Persist compaction checkpoints, timer deadlines, retry counts and crash-loop quarantine. A level-3 goal includes acceptance checks, budget/time/iteration limits, workspace/tool/network authority and allowed external effects; enforce these at worker/tool boundaries, not only in prompts. Approvals are durable scoped decisions tied to action arguments and policy version; absent clients leave forbidden work blocked. Revocation and cancellation propagate to descendants. Provider modes unable to enforce a requested policy must reject that autonomy capability or run inside a sufficiently constrained sandbox.
1. **Service extraction and capability contract.** Move lifecycle orchestration behind a reusable service; inventory each provider’s resume, streaming, steering and policy guarantees. Preserve CLI behavior and document accurate boundaries. Acceptance: CLI and in-process service contract tests agree. Related: open #476 (remaining sync/async UX), closed #571 (MCP foundation), #630 (host-background policy). Risk: ownership/environment behavior currently embedded in command handlers.
2. **Transactional execution ledger.** Add versioned session/task/event schema, idempotent submit and migration/import of existing JSON identities without deleting provider transcripts. Acceptance: duplicate requests create one task; fault injection cannot commit events without state. Related: closed #572 (earlier async dispatch), #519 (turn telemetry); these are reuse references, not evidence of durable execution. Risk: migration and retaining sensitive prompts/logs.
3. **Supervisor and recovery canary.** Add local server, leased workers, restart reconciliation, persisted backoff/quota wakeups and bounded crash quarantine. Start with turn-boundary recovery and explicit uncertain outcomes. Acceptance: kill client, worker and server separately; no competing writers, duplicate effects or lost terminal results. Related: closed #547 (detach), #603/#508 (quota refusal), open #293 (quota-interrupted roadmap recovery). Risk: opaque provider turns cannot offer tool-level exactly-once execution.
4. **Reconnectable client/event surface.** Add immediate task handles, cursor subscriptions, durable result/outbox delivery; migrate CLI/MCP and project server jobs into TUI. Acceptance: disconnect/reconnect shows all committed outcomes, with duplicate notifications deduplicated. Related: open #587 (MCP timeout), #611 (polling), #476; closed #630 deliberately hid async flags, so replace its completion guarantees before changing policy. Risk: slow consumers and hosts without completion callbacks.
5. **Goal policy and durable approvals.** Implement bounded unattended goals, objective verification, scoped policy, durable approval/revocation and cancellation trees. Acceptance: no connected UI is required for permitted work; disallowed effects block before execution; exhaustion and failed verification terminate predictably. Related: open #463 (escalation reasons), closed #694 (AGY tool enforcement). Risk: provider bypass flags are broader than Harnez policy; require capability checks and isolation.
6. **Adapters and deeper durability.** Canary ACP/editor and web clients, then Slack/chat/cloud adapters with authenticated principal-to-session mapping; add portable handoff branches and tool-level checkpoints only through capable runtimes, potentially a Pi Durable worker bridge. Acceptance: two client types steer one session; remote authorization prevents cross-user access; crash tests distinguish safe replay from uncertain effects. Related: closed #740/#742/#743/#747 (Claude channel/plugin lineage), open #646/#675 (compaction gaps), #725 (external Pi telemetry). Risk: adapter protocol churn, credential isolation and lossy provider handoffs; validate before promising “any client/any provider.”

## Pi Pocket / Pi Durable research for Harnez

Read-only audit, 2026-10-20. Sources: [Pi Durable guide](https://tannermidd.github.io/pi-pocket/durable.html), [Pi Pocket architecture](https://tannermidd.github.io/pi-pocket/architecture.html), [Pi Pocket engineering](https://tannermidd.github.io/pi-pocket/engineering.html), [repository](https://github.com/TannerMidd/pi-pocket), and [README](https://github.com/TannerMidd/pi-pocket#readme). Pi Durable is explicitly experimental; pin/test its version if integrating it.

## Definitions and “level 3”

Pi Durable calls itself “an agent harness that stores each step before it shows the step.” A task is a small state machine checkpointed after each step; model generation, tools and compaction are tasks. A commit atomically applies some combination of transcript entries, documents and tasks. Clients display committed state; reopening the same storage continues unfinished work. Pi Pocket is a separate web application over this harness, adding multiple users, phone/remote access and shared session controls.

The requested durable guide does **not** define “Level 3,” “out of the loop,” or any level taxonomy. It describes continued execution after process/client departure as a capability, not a numbered autonomy level. Pi Pocket calls this “work that starts without you” and documents schedules, triggers and unattended `/until` checks. Treat “level 3 = out of the loop” as the requester’s operational definition, not a Pi Pocket or Pi Durable classification.

## Architecture and operational semantics

- **Processes / client split:** Pi Pocket is one Node.js server process and one SQLite file; browser clients use the web app and receive committed updates over server-sent events. The server owns the durable harness and coordinator. Key paths: `src/server/app.ts` (harness/coordinator, tabs, sessions), `room.ts` (shared conversation view), `http.ts`/`http/` (JSON API, SSE), `projection.ts` (browser projection), `bin/pi-pocket.js` and `src/launcher/` (launcher/supervisor). One server at a time may use a DB; the storage does not itself fence a second process.
- **Storage:** `~/.pi-pocket/pocket.sqlite` contains Pi Durable transcript/documents/tasks/submissions plus Pocket documents (sessions, chat, pins, notes, schedules, goals, spend, etc.). Config, people/tokens, push subscriptions, uploads, worktrees, extensions and browser profile live beside it under `~/.pi-pocket/`. SQLite WAL with `synchronous=NORMAL` survives process crash but may lose the newest commit on host/power failure. Documents and transcript changes that must agree share a commit. See guide storage section and `src/server/docs.ts`.
- **Events / resume:** generation → tool tasks → generation form a task chain. On restart `resume()` schedules persisted unfinished tasks. `requestId` makes retried admission return the original submission; schedules and reports reuse IDs. Safe calls can replay; unsafe calls (examples: bash/browser/subagent) are reported interrupted to the model for inspection, not automatically repeated. This avoids claiming exactly-once external effects. Task hooks memoize approvals/goal checks so recovery does not ask twice. Partial streams are committed about every 100ms; a process kill can lose the current uncommitted chunk. `watch()` gives current view plus commit operations, not old commit replay; late clients take a current snapshot. Slow watchers are bounded (100 frames then newest view); Pocket coalesces commit updates before SSE delivery.
- **Human controls / unattended work:** Pocket adds durable inbox steering/queueing, scheduled messages, GitHub watches/webhooks, background subagents, PiP reporting, `/until` bounded verification, and push when work finishes or needs approval. Its extension hooks implement Lancet Guard: bash/write/edit calls can pause for an allow/deny decision stored across restart; plan mode also blocks changes pending approval. Push can allow/deny some approvals. Thus the human can leave during permitted work, while gated actions remain blocked pending a person. Guard is off by default, and steering users can run commands as the host user—an explicit security limit, not a sandbox. Code: `src/server/extensions/` (guard, goals, schedules, subagents, triggers), `src/server/push.ts`, `alerts.ts`, `goals.ts`, `schedules.ts`.

## Harnez mapping and roadmap implications

Prior Harnez reports correctly distinguish Pi Durable from Pi Pocket and correctly identify Harnez’s gap: `internal/subagent/session.go` persists session metadata/identity, while `driver.go` and `resume.go` invoke provider-native turns; this is not a per-step execution journal. `cmd/harnez/agent_run.go` owns CLI orchestration. `internal/mcp/server.go` is a stdio lifecycle adapter, not a durable server. `internal/tui/jobs/jobs.go` owns process groups in memory. `internal/channel/` tracks delivery receipts, but acceptance is not provider receipt/completion. These paths imply the earlier proposal for an extracted service plus scheduler/store remains sound.

Pi Pocket **confirms** atomic state+event persistence, request-id idempotency, durable queued input/timers, explicit replay safety, bounded live observation, and recoverable approval decisions as the right primitives. It **adds** concrete guidance missing from the roadmap: define crash guarantees at commit boundaries (including stream-loss window); persist policy/hook decisions as task memos; model background work through ownership/anchor tasks; identify a requester/principal for spend, approval and notification attribution; keep one-writer ownership explicit; and let reconnecting clients take a snapshot rather than depending on infinite event replay. It also reinforces that “durable” is not exactly-once side effects or automatic human absence: unsafe tools need reconciliation, and approvals can intentionally stop unattended progress.

**Adopt for Harnez:** (1) Build an execution ledger around submissions, attempts, task ownership, checkpoint/event/outbox records, idempotency keys and replay policy; retain provider transcripts as provider-owned history. (2) Start recovery at turn boundaries and surface uncertain external effects; only add tool-level replay where adapters can prove safety. (3) Persist inbox items, timers, approval decisions and notification state alongside tasks; use bounded cursor events plus snapshot-on-reconnect. (4) Carry authenticated requester identity through descendants for policy, quotas, spend and notifications. (5) Specify “out of the loop” as bounded delegated authority with acceptance checks, limits and durable blocked outcomes; approval-gated actions remain blocked until authorized. Pi Pocket’s SQLite/single-process design is a useful canary, not a drop-in Harnez architecture: Harnez is multi-provider Go and needs an adapter/service boundary, provider capability checks, and likely a transactional store with explicit worker leases/fencing before multiple workers.

## Pi Pocket architecture comparison for Harnez

Read-only architecture audit, 2026-10-20. Primary source: [Pi Pocket architecture](https://tannermidd.github.io/pi-pocket/architecture.html); supporting paths and deployment/security constraints: [Pi Pocket repository README](https://github.com/TannerMidd/pi-pocket).

## Architecture facts

- **Process and components:** one Node.js 22.19+ process and one SQLite file; TypeScript web app uses Preact + htm as plain ES modules. `bin/pi-pocket.js` enters `src/launcher/`; `src/server/app.ts` is the durable harness/coordinator, and `src/server/room.ts` owns a conversation's shared live view. JSON API/SSE are in `src/server/http.ts` and `http/`; committed-state browser projection is `src/server/projection.ts`; UI is `web/`.
- **Data:** `pocket.sqlite` stores Pi Durable transcript and documents alongside Pocket docs (sessions, chat, pins, notes, artifacts, subagents, schedules, goals, spend); each document kind defines fork-copy/empty behavior. `~/.pi-pocket/config.json` contains people, roles, hashed tokens and settings; `push.json` holds VAPID keys/subscriptions; uploads, worktrees, extensions and browser profile are sibling directories. Config writes are atomic, mode 0600; renaming a document kind is unsafe because Pi Durable checks scope/history/fork settings.
- **Commit/event flow:** commit changes can arrive unordered. One listener in `app.ts` does two synchronous passes, avoiding listener-registration-order effects on spend. It must not call harness session APIs; author recording is deferred with `setImmediate`, then missing authors are repaired at startup. Room changes coalesce around 90 ms; session list/subagent board around 400 ms; peek tiles around 1 s. SSE sends committed views/updates, not every commit; reconnecting clients get a current snapshot.
- **Attribution/protocol:** `src/server/attribution.ts` and `requests.ts` use request IDs `u:<user>:<key>` (human-authored) and `p:<user>:<key>` (sent on a user's behalf). Newest attributable message determines requester for spend, approvals, schedules and subagents; fallback is session starter, then owner. Scheduled human-created messages preserve the human `u:` identity.
- **Durability details:** schedules are durable tasks with send time in `pocket.schedules`; overdue work sends once after restart. Hook answers (approval, goal check) are task memos. Shell `!` request IDs persist in `pocket.shell-requests` until accepted. Fork cleanup of chat, later pins and authors occurs in the same commit as fork creation. Extensions in `src/server/extensions/` use prompt sections, tools, hooks and tasks; subagents have separate conversations with durable anchor/reporter tasks.
- **Security boundary:** this is access control, not execution isolation. Steering users can run commands as the host user and reach its files/tokens; per-session invites limit app visibility, not agent reach. Lancet Guard is off by default and approval by a steering user is not a separate privilege boundary. README says only one server process may use the DB. Remote modes include LAN plain HTTP, Cloudflare tunnel HTTPS, and encrypted Tailscale.

## Comparison to `docs/HarnezServerArchitecture.md`

- **Confirms:** one coordinator owning commits, transactional task/event/outbox state, requester propagation, persisted approval decisions, idempotent submissions, snapshot-on-reconnect, and explicit safe-replay versus uncertain side effects all fit Pi Pocket's operating model.
- **Adds:** specify commit-listener ordering constraints and prohibit reentrant harness writes; defer follow-on writes. Define author-attribution repair and document fork policy/atomic fork cleanup. Treat durable timers, request-ID retention, and task memos as first-class recovery cases. Coalesce client updates at bounded intervals and serve snapshots to late/slow clients.
- **Distinction/risk:** Pi Pocket relies on Pi Durable's integrated transcript/documents, whereas Harnez proposes provider-owned transcripts retained by reference and a provider-neutral ledger. Its single-process/single-DB design does not validate Harnez's multi-worker lease/fencing model; Harnez needs those protections. Likewise Pocket's steering and optional guard are not a sandbox, so Harnez's proposed tool/network enforcement must be enforced at worker/tool boundaries.

## Ticket-sized ideas

1. **Commit listener contract:** document/test unordered change batches, two-pass deterministic processing, deferred writes, and startup repair of derived attribution. Risk: listener logic can silently affect billing/requester attribution.
2. **Durable timer recovery:** add a scheduler test/spec for before-due restart, overdue restart, and duplicate wake-up with one request ID. Risk: wall-clock changes and delivery boundary need explicit semantics.
3. **Fork document policy:** define per-record fork behavior and test atomic fork + cleanup of post-fork derived state. Risk: copied mutable docs can leak future state across branches.
4. **Streaming subscription contract:** define coalescing cadence, cursor semantics and snapshot fallback for reconnect/slow consumers. Risk: consumers must tolerate omitted intermediate frames while preserving final committed state.
5. **Principal boundary review:** carry authenticated requester through child tasks, but separately specify host execution privileges and approval authority. Risk: identity attribution alone does not constrain what a steering user or agent can access.

Source paths/details above: [architecture page](https://tannermidd.github.io/pi-pocket/architecture.html) and [repository README architecture/security sections](https://github.com/TannerMidd/pi-pocket#architecture).

## Pi Pocket product-scope comparison

Read-only audit (2026-10-20), focused on user-facing features, unattended work, multiplayer, mobile, and notifications. Sources: [home/product page](https://tannermidd.github.io/pi-pocket/), [feature tour](https://github.com/TannerMidd/pi-pocket/blob/main/docs/features.md), [architecture](https://tannermidd.github.io/pi-pocket/architecture.html), [security limits](https://github.com/TannerMidd/pi-pocket/blob/main/SECURITY.md). Compared with [`docs/HarnezServerArchitecture.md`](/home/uwe/projects/harnez/docs/HarnezServerArchitecture.md); the earlier Pi Pocket report was treated as baseline.

## Findings and design comparison

- **Product surface:** Pi Pocket is a self-hosted browser client for Pi (Node.js server, SQLite file `~/.pi-pocket/pocket.sqlite`), usable from desktop, phone, or Android Termux. It offers session list/run timeline, model selection, files/diffs/branches, built-in Chromium, artifacts, memory, forks/retries/worktrees, shell, skills, and per-person/session spend limits. The primary source names `src/server/app.ts` in its architecture diagram and `src/server/extensions/` for feature hooks; data outside DB includes `config.json`, `push.json`, uploads, worktrees, extensions, browser profile under `~/.pi-pocket/`.
- **Unattended work:** `/schedule` delivers one-time/repeating messages; `/until` runs a check after each answer (max five checks); `/watch` follows PR checks/reviews/comments (max ten messages); Triggers extension adds GitHub watches and signed webhooks; PiP can watch repos, launch and follow sessions, schedule work, and push a short completion report. Work is attributed to the setup user and their access/spend limit. Approval-gated calls still wait for a person. See `/schedule`, `/until`, `/watch`, `POST /hook/…`, `PiP` in the product page.
- **Multiplayer:** multiple people/devices see and steer shared sessions with presence, attribution, side chat, pins/reactions/shared notes, turn-taking, viewer/steerer roles, and short-lived single-use invite links/QR/codes. This is richer than Harnez’s generic “authenticated sessions” adapter goal; it confirms carrying requester identity through descendants. Pi Pocket’s steering grants shell-equivalent access as the host user; invites scope UI visibility, not filesystem reach, and worktrees/spend limits are not security sandboxes.
- **Mobile and notifications:** phone-first layout, browser dictation, home-screen install, Android “Share to Pi,” and back/swipe navigation; Android Termux can host the server. Push reports completion, approval needs, mentions, side chat and PiP reports; some short approvals can be answered from notification. Remote access modes are `--access local|lan|cloudflare|tailscale`; push/dictation require HTTPS (or localhost for dictation).
- **Confirms Harnez proposal:** one durable service/store, queued input, schedules, request IDs, persisted approval decisions, requester identity, outbox notifications, and explicit boundaries on unsafe side effects align directly. Architecture calls PiP/subagents owned conversations and durable anchor/reporter tasks; path `src/server/extensions/` hosts most features. The server is single-process/one SQLite writer, so it does **not** validate Harnez’s multi-worker lease/fencing design; it is a simpler baseline.
- **Adds / sharpens:** user-facing “Running now” with cross-session Stop; bounded `/until` and PR-watch loops; per-user attribution/access/spend; turn-taking and viewer roles; phone-safe action surfaces; notification actions; remote access setup choices. Security page is candid: steer permission is effectively host command access; plan mode is not a boundary; Browser can reach localhost/network and bypass Lancet Guard. Harnez’s policy/tool-boundary enforcement should remain stronger than prompt/UI gating.

## Ticket-sized adoption ideas (priority order)

1. **Durable schedules + inbox steering:** persist queued messages and one-shot/repeating timers, deduplicate delivery by request ID, cancel when principal loses authority or budget. Risk: timezone/DST, duplicate external triggers, stale permissions.
2. **“Running now” cross-session view and stop:** aggregate active runs, tools, subagents, timers, and approval waits; expose cancellation handles in TUI/web/API. Risk: cancellation must propagate through child-task trees and accurately reflect provider limits.
3. **Bounded completion checks:** add `/until <check>`-like acceptance check with explicit count/time/spend ceilings and captured output; classify checks as replay-safe or mark interrupted/uncertain. Risk: checks execute code and may have side effects; require policy gate.
4. **Principal and notification contract:** carry requester through scheduled/webhook/subagent tasks; define role-scoped visibility and durable notification outbox with completion/approval/mention events. Risk: multi-user auth and push-token handling substantially expand threat surface; approval-from-push needs short-command/strong-auth constraints.
5. **Mobile client canary:** start with responsive status, logs, stop, and approval view over authenticated SSE plus snapshot-on-reconnect; defer full session editing. Risk: remote access exposes a host-execution harness; require TLS/auth and document that roles do not sandbox tools.

## Implications for Harnez

- **Confirms:** Harnez’s transaction boundary, idempotent submit, durable task/approval/inbox state, explicit unsafe-step recovery, and snapshot-on-reconnect are sound priorities. Pocket demonstrates that extension hooks can memoize durable decisions and that background schedules/subagents can be composed as task workflows.
- **Adds:** design live SSE and durable event subscriptions as separate products; bound slow-client memory and provide polling fallback. Model services around committed store publications rather than browser-specific events. Keep runtime extension APIs explicitly privileged.
- **Contradicts / limits:** Pocket’s SSE does not validate Harnez’s proposed durable cursor/outbox semantics; it intentionally reconstructs a current view. Its SQLite Harness does not establish multi-worker safety, leases/fencing, multi-provider continuation, or a general execution ledger. Do not infer host-power durability or exactly-once side effects from process restart tests.
- **Ticket-sized ideas:** (1) specify a service contract for commit publication, snapshot resync, and separately retained client notification cursors; risk: duplicate/reordered delivery semantics need definition. (2) add a recovery matrix test for each driver boundary: before/after submit, provider turn, tool side effect, and approval; risk: provider capabilities differ. (3) prototype persisted approval/task memo and requester propagation through one Harnez tool path; risk: stale policy must not authorize a changed request. (4) document and test SSE/poll slow-consumer bounds once the server API exists; risk: disconnect requires clients to resync and may drop transient stream chunks.
